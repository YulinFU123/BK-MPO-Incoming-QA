# 数据与配置迁移边界

本轮没有业务数据库迁移。`vault.json`、`.qav`、`.eap`、原 BI 数据目录、二维码 `.v2.bin` 和原导入导出协议不变。不要将配置 SQLite 当作业务数据库或把旧业务库写入其中。

## 首次使用

普通用户目录新增 `ExceptionAnalysisPlatformPreview/workbench-state-v1/modules.sqlite`。不存在时初始化专用 schema 1；不接受已有无关数据库，较高 schema 拒绝打开且不覆盖。使用应用标识、完整性检查、事务和修订号。

全局主题/紧凑行高第一次读取旧 `qa-workbench-theme`、`qa-workbench-compact`，只读取旧键，不删除或覆盖；然后保存新全局配置。二维码旧记忆仍由原代码只读兼容，BI 原配置仍由原引擎管理。没有将所有旧配置自动迁移的脚本，也不应对正式业务配置进行猜测转换。

不同模块用独立配置条目，工作区由宿主文件路径哈希标识，模板 ID 加入键。配置优先级为默认值、持久化配置、当前临时修改；全局界面只作用于界面，不能覆盖业务模块的同名字段。未来模块默认和工作区专属方案扩展需继续显式合并，不允许用一个大对象覆盖所有模块。

## 备份

- 业务记录：沿用 `.eap` 完整加密备份；原异常记录和 BI 原备份仍分别保留。
- 新配置：配置记忆 → 界面与安全 → 备份全部配置。在线备份包含该库的全部加密配置与可用历史。
- **必须保留同一 Windows 账户和原用户配置中的 `Local State` 提供器密钥。单独 SQLite 文件不构成跨电脑灾难恢复包。** 不得公开、覆盖或删除用户配置目录。
- 二维码记忆、原 BI 配置和原业务草稿尚未包含在新配置备份中；继续保留各自原备份。

## 恢复

单模块损坏：原密文保留，界面使用安全默认值并提示；选择可用历史版本恢复，恢复生成新修订，不直接改坏旧修订。没有有效恢复前拒绝自动覆盖。

配置库可打开时，可勾选确认，再从独立配置备份只读恢复当前模块。备份内容/路径绑定/账户必须匹配；未选择文件是取消，不当成成功。恢复仅替换选中的模块配置。

整库损坏时应用不会删库重建。`scripts/recover-module-store.js` 只读取有效备份并生成一个**新的**恢复文件，检查完整性，不覆盖活动库。需正常关闭全部工作台、保留损坏库及其 WAL/SHM、由维护人员将新的恢复文件放回配置路径；原 Windows 加密用户配置也必须保留。此流程尚未做成应用内一键恢复。

示例：`node scripts/recover-module-store.js <配置备份.sqlite> <尚不存在的恢复文件.sqlite>`。随包 Electron 可在 Node 模式运行该脚本；不需要下载 Node 或管理员权限。不要复制示例尖括号作为实际路径。

文件移动、路径改变、跨电脑和不同 Windows 账户的配置迁移将在稳定工作区 ID/便携备份阶段实施。本轮不得以此宣称支持。
