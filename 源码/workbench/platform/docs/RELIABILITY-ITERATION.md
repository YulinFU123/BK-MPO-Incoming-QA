# 保存可靠性迭代报告

2026-10-29 · 源码 0.9.0-dev.2 · 基线 0.9.0-dev.1。**源码开发增量，未发布新版 EXE，QA-WINDOWS-SAVE-001 未解决。**

## 本轮实际改动

1. 完整优化计划已写入 `OPTIMIZATION-ROADMAP.md`，覆盖保存、全部模块记忆、导航、工作区/模板、导入/分析、回归发布，并给出逐阶段门槛。
2. 开始修改前，197 个非生成源码文件与 0.9.0-dev.1 交付快照校验一致。生成的 Python 缓存不作为发布源码。旧当前作业整体归档到 `构建/历史作业/0.9.0-dev.1`，原审阅包 SHA-256 核对一致，不删除历史，不替换在用程序。
3. `adapters/encrypted/repository.js` 细分创建/写入/同步/关闭临时文件、检查目标、初次发布和替换原文件阶段。失败详情只包含错误码、阶段、尝试次数、耗时和清理结果，不包含公司数据或完整路径。
4. 创建临时文件未成功时，不再尝试删除该名字的文件；只有本次独占创建的临时文件允许清理。该边界修正不等于保存间歇故障根因已修复。
5. 保存失败提示明确保留输入；空间不足与权限/占用提供不同检查方向。没有删除目标文件、复制覆盖或无限重试等降级写入。
6. 新增 `scripts/check-storage-reliability.js`，只创建新合成库，覆盖同步旧记录保存、异步事务、失败后原字节/缓存检查、显式重试和重新打开核对。
7. 新增 `scripts/storage-diagnostics.cjs`，只有 QA 启动时明确指定目录才启用。记录原始 Windows 重命名错误和安全元数据；拒绝 QA 范围外输出；日志失败不改变业务错误。未接入正式程序的常驻日志。

表中测试文件均在 `构建/历史作业/0.9.0-dev.2/` 下。“900+1200 次”是两种运行时、两个版本状态的不同实验，不能合并为新版 2100 次验收；重试回滚检查在无失败的压力运行中没有触发，不能算作该实验已覆盖故障分支。

末次失败发生于 `storage-failure.test.js` 恢复原始文件操作后再次调用保存，错误来自真实 Windows `rename`，不是预期注入的 `EIO`。新增观察器捕获 `EPERM`、errno `-4048`，源和目标均为存在的普通文件，模式未标只读。**这不能证明 ACL、外部占用、文件系统过滤器或其他原因中的任何一个是根因。** 原文件保护测试通过不代表所有生产失败均已安全验收。

## 未验证与未实施

- 没有新增可见界面布局，本轮未重跑 GPT 页面验收，不继承为“新版界面全通过”；原浏览器版本断言只同步源码版本。
- 未解密、未试写正式 vault、真实 `.eap` 或公司 BI；现有业务格式、存储路径和加密算法未修改。
- 未构建新版 EXE，已交付的 0.9.0-dev.1 程序保持原样；没有公司普通账户、真实扫码枪、Office、打印、DPI、断电与长稳验收。
- 旧录入草稿/查询、二维码和 BI 配置全面迁移尚未开始；内部多工作区、模板版本、自适应导入和全局分析仍按路线后续实施。

## 明确继续入口

1. 使用本轮失败日志与 QA 预加载诊断，在同样并发条件下复现；区分目标与临时源文件的共享/访问失败。只观察合成 QA 文件，不关闭外部进程，不调整公司安全策略。
2. 排查仓储自身句柄生命周期、同步桥接阻塞和关闭顺序；必要时建立单独的受控 Win32 探针。没有证据前不无限延长重试或绕过原子替换。
3. 确定原因后再做最小修复，补失败复现 → 修复后通过的用例，核对重启/备份/改密/锁定/导入及并发回归。
4. 满足保存门槛后进入原录入草稿和查询/跟进的统一记忆接入。

当前源码测试入口为 `构建/维护工作台.ps1 -Action Test`（现在执行当前开发源码，并非重放0.9.0-dev.2）；随包 Electron 只作为固定运行环境执行开发源码，不表示发布程序已升级。精确的本轮运行参数在 `构建/历史作业/0.9.0-dev.2/工具/run_reliability.py`。主动诊断使用 `--require scripts/storage-diagnostics.cjs`，且必须同时设置隔离的 `PLATFORM_QA_ROOT` 与其内部的 `PLATFORM_STORAGE_DIAGNOSTICS`。
