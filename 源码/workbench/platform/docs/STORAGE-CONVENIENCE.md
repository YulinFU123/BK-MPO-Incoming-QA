# 存储占用自动恢复

本次基于0.20.1-dev.1修复“分析存储已被其他进程使用，或存在需要人工核对的锁文件”。实机发现两个标准锁分别指向已经退出的进程；此前每次碰到锁文件都直接拒绝打开，没有核对拥有者是否还存在。

启动仍进入工作区管理，托管工作区使用本机自动保护，不要求用户创建或输入密码。原密码文件的读取流程保留。取消加密本身不能解决并发占用，本轮先解决已确认的卡点，没有将旧数据转换成明文。

## 使用

正常打开当前版本，选择原工作区。程序自动恢复已退出进程遗留的标准占用锁，无需手工清理文件。再次点击启动入口会唤回已有窗口；最小化时先恢复窗口，编辑草稿保留。

若确有另一个进程正在使用工作区，返回已有窗口或正常关闭后重试。程序不结束其他进程，不把权限无法确认、内容不明或活进程的锁当作已退出。不要删除业务文件解决占用。

## 数据边界与兼容性

原EAP数据、AES-GCM协议、密码、Windows保护配置、导入规则、分析数据库、草稿和路径都保持兼容。没有数据模型迁移，亦未更换分析数据来源。二维码和条形码标签、手工记录、自定义字段、跟进、原BI、原生BI、工作区独立记忆、班次和产品类型名称保留。

每个EAP旁新增`.lock.sqlite`协调文件，由现有内置SQLite提供操作系统锁，不新增安装依赖；该文件不含业务记录或密钥。进程异常退出时系统自动释放锁，下次打开先串行核对旧`.lock`中的进程，再恢复。保留旧`.lock`协议防止早期版本同时写入；没有按年龄强行解锁。

## 备份与回退

源文件修改前完整副本与校验在本作业发布记录；当前/上一两个完整离线程序独立保留。对实机残留锁处理前保存EAP和锁副本并记录SHA-256，处理后核对业务文件字节不变。实际工作区不会因修复而重新导入或重算。

回退时正常关闭程序，从上一版本入口启动。同一EAP仍可直接读取，无需反向迁移。`.lock.sqlite`无需删除；旧版忽略此协调文件，但它没有本版的崩溃锁自动恢复能力。若需恢复业务备份，请先保留现有业务文件，再按原备份流程操作，勿用旧备份覆盖较新的记录。

## 验证与限制

自动化覆盖强制结束写入进程后恢复、四个进程同时恢复仅一个成功、活进程与权限未知锁保留、替代锁不被错误释放、失败写入释放协调锁、损坏协调库保留原数据、重复启动事件，以及原加密、配置、记录、BI、标签回归。

本轮不把原间歇保存错误QA-WINDOWS-SAVE-001标为解决。该错误发生在替换业务文件时，与本次已确认的残留占用锁不同。实际Windows可见窗口、公司电脑策略、扫描枪及打印仍未验收；隐藏后端测试和打包成功不能替代这些验收。
